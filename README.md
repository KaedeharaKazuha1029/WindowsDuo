# WindowsDuo

在 Windows / macOS 笔记本上复刻 **iPhone Duo 折叠屏的「悬浮玻璃」效果**：屏幕开合时，桌面内容像隔着一层绕铰链旋转的玻璃——开合角度越大，内容越模糊、越暗，视线出界处渐变为纯黑。

> **✅ 硬件通路已端到端打通（2026-09-27）**
>
> Windows 端软件（着色器、抓屏、键盘、串口自适应、按需显示）与 **ESP32 + MPU6050 硬件链路**均已在本机实测通过，详见「[测试情况](#测试情况)」。
>
> - ✅ Windows 端：GL 3.3 core 渲染、DXGI 抓屏、键盘、串口自适应、按需显示全部实测通过
> - ✅ ESP32 侧：**YD-ESP32-S3 (N16R8)** + MPU6050，本机 ESP-IDF v5.3.1 编译、烧录（`verify_flash` 全 matched）、启动、USB 日志通路均验证；传感器识别与零漂校准通过，串口稳定 **100 Hz**
> - ✅ 联调：**开合盖子真实驱动玻璃浓度**——全开 0%，合到底实测峰值 90.7%，中间单调（分档数据见下）
> - 装法特例：本机模块是 **X 轴平行转轴**贴的，所以 `win/config.json` 用 `"axis": "b"`（不用重烧固件）
>
> **接线与烧录步骤**见 [`esp32/mpu6050_angle/README.md`](esp32/mpu6050_angle/README.md)；**端到端操作流程**（接线 → 标定 → 运行 → 调参 → 排障）见「[快速开始](#快速开始)」。

## 效果原理

这不是简单的全屏高斯模糊，而是**空间化的逆投影**：

- 桌面内容固定在世界空间的平面上不动，屏幕则是一块绕底边铰链向观察者旋转的"玻璃"
- 每个像素从眼睛发射线穿过玻璃像素，交到界面平面上得到采样点
- 间隙越大 → 采样半径越大（模糊越强）、衰减越多（越暗）；靠近铰链处始终清晰
- 采样使用 Vogel 螺旋盘 + mip LOD 分级 + 边缘覆盖率平滑，单 pass GLSL 着色器完成

理论模型参考自多个开源复刻（DuoLikeAnimation / iphone-duo / MacDuo / FrostFold），按笔记本场景（铰链 = 屏幕底边）重新实现。

## 改了什么

**1. 着色器：兼容式 → GLSL 330 core（核心修复）**

- `VS` 改成 `layout(location=0/1) in` + `out`，`FS_DUO` 改成 `in/out vec4 fragColor`，6 处 `gl_FragColor` 全部替换。
- `_draw_quad` 从立即模式 `glBegin/glVertex` 改成 `initializeGL` 里建 **VAO+VBO**、`glDrawArrays(GL_TRIANGLE_FAN)`。

原因：Intel Windows 驱动的兼容模式只到 GLSL 1.20（本机实测 `#version 120` 通过、`130` 与 `330 compatibility` 均被拒，报 `'varying' : not available in current GLSL version`）。原写法在这类驱动上**必然编译失败**，而失败后程序会直接崩掉（见第 2 条），所以这是一个"跑不起来"级别的修复。

**2. 着色器失败不再"猝死"** 原来编译失败后仍去调 `glUniform1i` → `GLError 1282` → 进程直接挂掉。现在 `_gl_linked` 为假时只清黑屏并打印明确原因；非 smoke 模式下 1.5 s 后自动退出（exit 2），不会给你留一个全屏黑窗。同时修了 `int(f.profile())` 在 PyQt6 上抛 `TypeError`、以及 GBK 控制台下 `✔/✘` 抛 `UnicodeEncodeError` 导致自检崩溃这两个原有 bug。

**3. 串口自适应** 新增 `candidate_ports()`：按 Espressif 原生 USB(303A) > CH340(1A86) > CP210x(10C4) 排序自动挑口；`AngleReader` 逐个尝试、被占用/拔出后 0.6 s 自愈重扫；支持 `--port COMx` 手动指定。`config.json` 的 `port` 从写死的 COM3 改为 `"auto"`（COM3 是原作者机器的口）。

**4. 其它适配** `mss.mss()` → `mss.MSS()`（mss 10.2 已弃用）；`--smoke` 支持 `--g 0.35` 指定浓度并加了 `HoldControl`（原来浓度会被键盘线程拉回 0，演示帧等于没效果）；两个 `.bat` 不再写死 `C:\Users\Kazuha\...`；`offscreen_test.py` 同步 core 化。

**5. 浓度拉高不再整屏变黑**（`max_tilt_deg`: 88 → 60）

原版把浓度 100% 映射到 88° 倾角，而着色器的逆投影在 65°~75° 之间就会让视线全部射出界面平面。实测（同一张测试图）：85% 浓度时 95% 的像素已变黑，100% 时亮度 0.1/255、**99.9% 全黑**——也就是"浓度拉到一半以上屏幕就黑了"。改成 60° 后拉满仍是"强磨砂 + 四角压暗"：亮度 60.3/255、全黑像素 25%。想保留原版"折到底变黑"的手感，把该值调回 88 即可。

**6. 抓屏后端换成 DXGI，拖动时玻璃内画面更新快 6 倍**（`capture`: `auto`）

原版用 mss（GDI `BitBlt`）：整屏 1920×1080 单次中位 **33.3 ms**（≈30 Hz 封顶），实测程序里 72~84 ms，所以只能 3 Hz 刷新——拖动窗口时玻璃里就是一张 3 fps 的"冻屏"。现在 `auto` 优先走 **DXGI Desktop Duplication**（`dxcam`）：单次中位 **6.6 ms**、稳定拿到 60 fps 新帧。模拟拖动实测玻璃内画面更新 **3.0 fps → 18.6 fps**，进程 CPU 36% → 50%（单核百分比）。未安装 `dxcam`/`numpy`、或初始化失败时**自动回退 GDI**，行为与原来一致。

**7. 窗口比屏幕少几像素**（`win_shrink_px`: 2）

**这是让 DXGI 可用的前提**：恰好铺满物理屏幕的窗口会被 Windows 走"全屏直通"呈现，DXGI 抓屏会把整块抓成**纯黑**（GDI 则是完全看不到它）。窗口少几行后回到普通合成路径，抓屏才能拿到真实桌面。少掉的那几行在屏幕最底部（= 铰链处，本来就接近清晰），视觉上看不出来。

**为什么是 2 而不是 1**：这个值要经过 `round((物理高 − N) / dpr)` 换算成逻辑尺寸，dpr 不是整数时会被四舍五入。实测：dpr=1.25（125%）时 1 就够；但 **200% 缩放（4K 笔记本常见）下 `1` 会被算回满屏**，DXGI 又抓到纯黑（窗口物理高 1080/1080、抓到的中心 R=0）。改成 2 后，125% 与 200% 下都稳定少 2px、抓屏正常。

副作用需注意：窗口不再是"满屏"，抓屏就真的能看到它了，于是 `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` 的自我排除从"锦上添花"变成**必须生效**（代码里保留，设置失败会打印警告；别删这段）。

**8. 刷新率 3Hz → 30Hz**（`refresh_hz`）

DXGI 变便宜之后 30Hz 才有意义；实测 60Hz 与 30Hz 结果相同（瓶颈已不在本项目这侧）。嫌 CPU 高可调 15，想省电可调 3~5。

**9. 修复 `←` / `a` 清空键无反应**

原版把"清零"编码成 `delta = 0.0` 哨兵值，但判断条件是 `abs(delta) < 0.5`，于是走了"在当前值上累加"分支 → `target + 0.0` 等于原值不变（而 `→` 的 `1.0` 不满足条件、走 else 直接赋值，所以一直正常）。现已拆成"拉满 / 清零 / 微调"三个分支。

**10. 两个 `.bat` 换掉解释器写法**

- **纯 ASCII**：AGENTS.md 第 4 条要求 bat 只能是 ASCII——原先注释里的中文经 cmd 的 GBK 解码会把两行 `REM` 粘连在一起。
- **不再写死 `py -3.14`**：原来的 `where py && set PY=py -3.14` 在只装了 3.12/3.11 的机器上会直接报 `No runtime installed that matches 3.14` 然后 `pause`，**不会**回退。现在按 `py -3.14 → 3.13 → 3.12 → 3.11 → py -3 → python` 依次探测，且探测命令里直接 `import PyQt6, OpenGL, mss, serial`——即"挑一个依赖齐全的解释器"，全都不可用时打印 pip 安装命令。
  探测用**标准输出**而不是 `errorlevel`：实测 `py` 启动器在版本不存在时返回的是**负数退出码**，`if not errorlevel 1` 会把它误判成"成功"（这正是第一版回退逻辑没生效的原因）。
- 顺带统一为 CRLF 行尾（Windows 批处理的常规格式；仓库里原本是 LF）。

**11. 玻璃不再被任务栏压住**（`keep_on_top_hz`: 2）

任务栏 `Shell_TrayWnd` 自己也带 `WS_EX_TOPMOST`。程序刚启动时，我们的置顶窗口在置顶带最前面、盖得住任务栏；但**只要真实点击一次任务栏**（点它的空白处、时钟等），资源管理器就会把任务栏插到置顶带最前，压到悬浮层之上——此后玻璃就盖不住任务栏了（表现为"改玻璃时任务栏不跟着一起变"，而且不会自己恢复）。根因是 Qt 的 `WindowStaysOnTopHint` **只在创建窗口时声明一次** `WS_EX_TOPMOST`，之后不会重申。

现在 `tick()` 每 `1 / keep_on_top_hz` 秒调用一次 `raise_()`（对 topmost 窗口即"移到置顶带最前"，带 `SWP_NOACTIVATE`、不抢焦点）。实测：关闭该功能时点任务栏 → 层序变成任务栏在上、一直不恢复；开启后点任务栏 → 1 秒内自动回到最上面。设为 `0` 可关闭此行为。

**12. 按需显示：浓度≈0 时收起玻璃并停掉抓屏/渲染**（`visible_eps`: 0.005、`hidden_refresh_hz`: 0）

原先窗口从启动到退出一直盖在屏幕上，桌面永远是一张按 `refresh_hz` 更新的截图：拖动窗口、滚动页面都不跟手（画面更新率被抓屏速度卡住），而且抓屏与重绘的 CPU 一直付着。现在改为按需：

- `g ≤ visible_eps`（默认 0.5%）→ `hide()` 窗口，**并完全停止抓屏与重绘**；控制台状态行会标出 `[收起]`；
- `g > visible_eps` → 先补抓一帧"新的"截图（最多等 0.25 s，抓屏异常时不会卡住不出现），再 `show()`，避免抬起瞬间看到收起之前的旧画面。

实测（本机 1920×1080、DXGI）：

| 状态 | 累计抓屏 | 累计重绘 | CPU（单核） |
|---|---|---|---|
| 浓度 0%（收起 1.5 s） | +0 | +0 | 0.0% |
| 抬到 50% | +16 | +31 | — |
| 降回 0%（1.8 s 后） | +0 | +0 | 1.6%（含控制台刷新） |
| 再抬起 30% | 重新抓帧、重现显示 | — | — |

另外验证了"收起→抬起"多轮之后画面依然正常：两轮 60% 的渲染结果逐项一致（平均亮度 25.0 vs 25.0，标准差 24.66 vs 24.63），说明 `SetWindowDisplayAffinity` 在重新 `show()` 时仍然生效、没有被自己截进去。

实现上注意两点：

- **主循环定时器只建一次**。这版原来把 `QTimer` 建在 `showEvent()` 里，而按需显示会反复 `hide()/show()`，每次 show 都新建一个定时器会让 `tick` 被重复调用（旧的并不会自己停）。现在统一走 `start_tick()`，`showEvent` 里只做幂等调用。
- **收起时也要跑主循环**。窗口不显示就不会触发 `showEvent`，所以主循环必须在启动时（`main()` 里）就起来，否则没人把窗口叫回来。

想恢复"常显"就把 `visible_eps` 设成 `-1`（任何浓度都大于它）。

**13. ESP32 固件适配 YD-ESP32-S3（手头这块板子）**

原工程只针对 **ESP32 (D0WDQ6) + 掌控板**，引脚写死 `SCL=GPIO22 / SDA=GPIO23`。而手头这块是 **ESP32-S3 (YD-ESP32-S3 N16R8)**——**S3 根本没有 GPIO22/23**（只有 0–21、26–48），所以原样烧进去也跑不起来。改动：

- **按目标芯片自动选引脚**（`main/mpu6050_angle_main.c` 顶部）：`esp32s3` → `SDA=GPIO8 / SCL=GPIO9`；`esp32` → 仍 `23/22`。换板子只改 `idf.py set-target`，源码不用动。选 GPIO8/9 是因为它们不在 strapping、USB、UART0、板载 RGB、以及 N16R8 的 8MB PSRAM 占用之列。
- **日志带上板名与期望引脚**，接线时照着日志接即可（未接传感器时会打印具体引脚号）。
- **`sdkconfig.defaults[.<target>]`**：S3 = 16MB Flash + 控制台走内置 **USB-Serial-JTAG**（板子只有原生 USB 口，保持默认的 UART0 控制台会在 USB 上什么都看不到）；掌控板 = 2MB + UART0。
- **`run_build.py` / `build.bat` 修好**：原来写死 IDF 5.4.4 与 `D:\KaiFa\find\duo\esp32`（本机都不存在）。现在自动探测 `D:\Espressif` 下的 IDF 版本、python 环境与各工具目录，工程目录取脚本自己所在位置。
- **两个 IDF 坑**（docs 里没写清楚，已写进 `esp32/mpu6050_angle/README.md`）：
  1. 只有基文件 `sdkconfig.defaults` **存在**时，IDF 才会加载 `sdkconfig.defaults.<target>`（`project.cmake` 630–636 行），否则按目标的 defaults 被**静默忽略**；
  2. `sdkconfig.defaults*` 必须**纯 ASCII**——kconfgen 用系统 locale（GBK）读它，中文注释直接 `UnicodeDecodeError` 中断配置。

### 已验证（MPU6050 接入后 · 2026-09-27 端到端实测）

模块到货后接线（`VCC→3V3 / GND→GND / SCL→GPIO9 / SDA→GPIO8 / AD0→悬空`），实测：

| 项目 | 结果 |
|---|---|
| 传感器识别 | 固件启动读取 `WHO_AM_I`，零漂校准完成后开始输出（校准不通过就不会进入输出循环） |
| **芯片型号** | **实测 `WHO_AM_I = 0x70`，是 MPU6500 系，不是 0x68 的 MPU6050**（这类克隆模块很常见）。寄存器映射与量程换算一致，功能不受影响；ESP-IDF 版只打印不校验所以当年没发现 |
| 串口数据率 | Windows 端读到 `100Hz`（状态行 `[connected COM3 100Hz]`），长时间无丢帧、无 I2C 报错 |
| 轴向判定 | 动盖子时主轴 `a`（默认 AXIS_Y）只变 **15.6°**，副轴 `b`（AXIS_X）变 **67.9°** → 模块是 **X 轴平行转轴**贴的。**无需重烧固件**：把 `win/config.json` 的 `"axis"` 改成 `"b"` 即可（固件本来就同时输出两轴） |

| 死区 | `angle_open` 若贴着实测值取（-83.5 那种），噪声会让浓度在 0~1.2% 抖动导致窗口闪烁；留约 4 个单位死区（`glass_start=0.10`）后全开稳定为 0.0% |

### 未验证 / 已知限制

- **`lock_at_close`**（合盖锁屏）：未测。
- **浓度 100% 端点**：实测最高到 90.7%（测试脚本到 90% 即收工），100% 由标定值线性外推（`b = -38.35`）。
- **副轴 `b` 是纯加速度计角度**（没走互补滤波），静止噪声约 ±0.6°；Windows 端有一层 EMA 平滑（约 65ms 时间常数），实机看不出抖动。想要更平滑可以把主轴换回 `a`，那需要把固件改成"两轴都做互补滤波"后重烧一次。
- **"角度自动"模式**：已用端到端脚本验证（脚本直接以 `auto=True` 驱动，等价于按了 `r`）；真人按 `r` 的路径未单独回归。

### 后续计划

端到端链路已打通。剩下的是可选优化：① 固件两轴都做互补滤波（主轴更平滑，需要重烧一次）；② 按实际观感微调 `glass_start`（出玻璃的早晚）、`max_tilt_deg`（最浓时的糊度/暗度）、`refresh_hz`。

> 说明：原来的 `esp32/` 工程只针对 **ESP32 (D0WDQ6) + 掌控板**（引脚写死 `GPIO22/23`），在本机这块 S3 板子上跑不起来（S3 没有 GPIO22/23）。现已改成**按 `idf.py set-target` 自动选引脚**，两个目标共用一份源码；`esp32/mpu6050_angle/README.md` 里有完整的接线表与烧录步骤。

软件侧原先留着一个已知可优化项：**玻璃是常显的**（启动后桌面即变成截图回放）。现已加入按需显示（见「改了什么」第 12 条），平时桌面回到原生帧率。

## 快速开始

### Windows + ESP32

**1. 接线**（MPU6050 GY-521 ↔ 板子，四根线）

| 板子 | SDA | SCL |
|---|---|---|
| YD-ESP32-S3 (N16R8)（本机这块） | **GPIO8** | **GPIO9** |
| 乐动掌控1.0 / 掌控板 | P20 金手指 → GPIO23 | P19 金手指 → GPIO22 |

`VCC→3V3`、`GND→GND`、`AD0→GND 或悬空`（地址 0x68）、`INT/XDA/XCL` 不接。详见 [`esp32/mpu6050_angle/README.md`](esp32/mpu6050_angle/README.md)。

**2. 烧录固件**（本机 ESP-IDF v5.3.1；按住 BOOT + 点一下 RESET 进下载模式）

```
esp32\mpu6050_angle\build.bat -p COM3 flash
```

⚠️ 烧完**必须再按一下板上的 RESET**，芯片才会从 Flash 启动（USB-JTAG 板子上 `--after hard_reset` 无效）。

**3. 上电自检**（保持模块完全静止 3 秒，固件要做陀螺仪零漂校准）

```
I (xxx) mpu6050: WHO_AM_I = 0x68 (期望 0x68)
I (xxx) mpu6050: >>> 陀螺仪校准中... 请保持模块完全静止 3 秒 <<<
I (xxx) mpu6050: 校准完成! 零漂偏移: gx=.. gy=.. gz=..
I (xxx) mpu6050: 开始输出角度 @100Hz: {"a":主角度,"b":副轴角度}
```

**4. 标定角度（关键，不做这步玻璃不会动）**

```bat
python esp32\debug_view.py --port COM3
```

- **全开**笔记本（正常使用姿态）→ 记下 `a` → 填进 `win/config.json` 的 **`angle_open`**
- **合到最合** → 记下 `a` → 填进 **`angle_closed`**
- 约束：`angle_closed` 必须**大于** `angle_open`（固件约定：合盖方向 = 角度变大）。
  例：全开 `a=-92.4`、全合 `a=+8.1` → `"angle_open": -92.4, "angle_closed": 8.1`

方向不对就改固件顶部重烧：`a` 不动而 `b` 在动 → `HINGE_AXIS` 改 `AXIS_X`；合盖时 `a` 反而变小 → `HINGE_SIGN` 改 `-1`。

**实测案例（本机 YD-ESP32-S3 + MPU6050 模块，模块 X 轴平行转轴）**：动盖子时 `a` 只变 15°、`b` 变 68° —— 说明模块是 X 轴平行转轴贴的。这时**不用重烧固件**，把 `win/config.json` 的 `"axis"` 从 `"a"` 改成 `"b"` 即可（固件本来就同时输出两个轴）。

标定取两个位置各静止十几秒的均值，**并且 `angle_open` 要取"最不保守"的那个值（数值最大）**，这样任何开盖姿态都落在死区里：

| 位置 | 实测 `b`（多次） | 取值 |
|---|---|---|
| 全开 | -74.16 / -76.45 / -76.97 / -79.34 | `"angle_open": -74.2` |
| 合到底 | -36.49 / -36.92 | `"angle_closed": -36.7` |

映射结果：全开 0%、`b=-70` 起开始出玻璃、`b=-40` 时约 99%、合到底 100%，中间单调。

> **串口是独占的**：标定完记得关掉 `debug_view.py`，否则 Windows 端打不开串口。

**5. 运行 Windows 端**

```
win\run_overlay.bat
```

先**点一下控制台窗口**，按 **`r`** 切到"角度自动"（状态行会从 `[手动]` 变成 `[自动] a=.. b=..`）。然后合盖：全开时桌面原生（玻璃收起）、逐渐合上玻璃出现并变糊变暗、重新打开又消失。

键盘（需控制台焦点）：`↑/↓` 浓度 ±3%、`←` 清零、`→` 拉满、`r` 手动/自动、`Esc` 退出。
切到自动后可以**把控制台最小化**，避免黑底终端被截进玻璃里；要退出时 `Alt+Tab` 回来按 `Esc`。

**6. 调参**（都改 `win/config.json`，重启程序生效）

| 想要的效果 | 改哪个 |
|---|---|
| 合一点点就出玻璃 / 要合很多才出 | `glass_start` 调小 / 调大（默认 0.05） |
| 拉满时太黑太糊 | `max_tilt_deg` 调小（默认 60，**别超 70**）、`darkening` 调小 |
| 玻璃更跟手 | `refresh_hz` 30（装了 `dxcam` 才划算，否则降到 3~5 省 CPU） |
| 收起阈值（浓度≤它就完全停掉抓屏/渲染） | `visible_eps`（默认 0.005） |

**7. 排障**

| 现象 | 原因 | 处理 |
|---|---|---|
| 控制台 `等待串口` / `未发现串口` | 板子没插好 / 串口被占用 | 关掉 `debug_view.py`；设备管理器确认有 COM3 |
| `connected COM3` 但浓度一直 0% | 还在手动模式；或没有角度数据 | 按 `r`；看状态行 `a=` 是否有数 |
| 合盖浓度不动 | 没标定（默认 10/-90 是原作者的）或方向反了 | 回到第 4 步 |
| 开盖反而出玻璃 | `a` 方向与固件约定相反 | 固件 `HINGE_SIGN=-1` 重烧，或交换两个标定值 |
| I2C 时好时坏 / 一直 nack | SCL/SDA 接反、线太长、接触不良 | 检查接线；固件 `I2C_FREQ_HZ` 降到 `100000` 重烧 |
| 玻璃里有一块黑 | 截屏方案会把屏幕上任何黑底窗口如实截进去 | 最小化控制台（见第 5 步） |

**依赖**：`PyQt6 / PyOpenGL / mss / pyserial` 必需（`Pillow` 仅 `--smoke` 用，`dxcam + numpy` 可选——装了才走 DXGI 抓屏、拖动更跟手）：

```
python -m pip install PyQt6 PyOpenGL mss pyserial Pillow
python -m pip install dxcam numpy        # 可选
```

两个 `.bat` 启动时会**自动挑选一个依赖齐全的 Python 解释器**，全都没有则打印上面这条安装命令。

> **注意 1**：固件侧已验证到"烧录 + 启动 + 串口日志"（见「[测试情况](#测试情况)」）；**传感器、角度标定、端到端联调还没做过**（MPU6050 未到货）。当前纯手动模式（`run_manual.bat` + 键盘）是完整可用状态。
>
> **注意 2**：**必须从带控制台的窗口启动**（双击 `.bat` 或在 cmd 里运行），不要用 `pythonw`、图形化快捷方式等方式启动——那样键盘线程会失灵并把 CPU 跑满，详见「[在其它设备上运行](#在其它设备上运行纯手动模式)」。

## 在其它设备上运行（纯手动模式）

把这套东西拷到另一台 Windows 机器上、**不改任何代码**直接跑，需要满足以下几个前提（下表均为本机实测验证过的行为）：

| 前提 | 说明 | 不满足时 |
|---|---|---|
| **Windows** | 代码用到 `msvcrt` / `ctypes.windll` / `SetWindowDisplayAffinity` / DXGI | macOS / Linux 不行（仓库另有 `mac/` 实现） |
| **显卡驱动支持 OpenGL 3.3 core** | 远程桌面会话、纯虚拟机、刚装完系统还没装显卡驱动（微软基本显示适配器只有 GL 1.1）都不满足 | 启动约 1.5 s 后打印 `[致命] 着色器未链接, 无法渲染` 并以 exit code 2 退出（不会卡死黑屏，但用不了） |
| **依赖齐全** | `PyQt6` / `PyOpenGL` / `mss` / **`pyserial`**（手动模式并不用串口，但它是模块级 import）；`Pillow` 仅 `--smoke` 需要；`dxcam + numpy` 可选 | 启动即 ImportError；两个 `.bat` 会提前探测依赖并打印 pip 命令 |
| **Python ≥ 3.9** | 代码没有 3.10+ 专属语法 | `.bat` 会自动挑选可用的解释器 |
| **从带控制台的窗口启动** | 双击 `.bat`，或在 cmd 里 `python glass_overlay.py --manual`。**不要**用 `pythonw`、图形化快捷方式、或某些 IDE 的"无控制台运行" | 实测：`msvcrt.getwch()` 会立刻返回 `'\uffff'` 而不阻塞，键盘线程变成死循环——**所有按键失灵，且进程 CPU 由约 50% 升到 118%（单核）** |

参数上建议 `win_shrink_px` 保持 **2**：0 或 1 在部分 DPI 缩放比例下会让 DXGI 抓到纯黑（见「改了什么」第 7 条）。

### 拷过去之后先自检

```
cd win
python glass_overlay.py --smoke --manual --g 0.35     REM 跑 2 秒自动退出并抓帧
```

能正常退出（exit 0）就说明 GL 与抓屏都正常；若打印 `[致命] 着色器未链接` 则是显卡驱动不支持。
注意 `--selftest` **不覆盖着色器**（它不创建窗口，只测截屏与串口），别只用它判断能不能用。

### 只在特定环境才需要的降级（改 `config.json` 即可，无需改代码）

| 情况 | 建议配置 |
|---|---|
| Windows 10 低于 2004（不支持 `WDA_EXCLUDEFROMCAPTURE`） | `capture` 设 `"gdi"` + `win_shrink_px` 设 `0`（满屏窗口对 GDI 天然不可见，既不需要自我排除也不会反馈）。**不要**配成 `win_shrink_px: 0` + `capture: "auto"`，那样 DXGI 会抓到纯黑 |
| 多显示器 / 笔记本混合显卡 / HDR 显示器 / 播放受保护内容 | `capture` 设 `"gdi"`（DXGI 在混合显卡下可能选错输出，HDR 下返回浮点格式，受保护内容返回黑块） |
| 没装 `dxcam`（自动回退 GDI） | 依然可用：实测 GDI@30Hz 玻璃内画面 13.4 fps、CPU 44%（DXGI 为 18.6 fps / 50%）。想更省 CPU 可把 `refresh_hz` 调到 3~5 |

## 主要参数 (`config.json`)

| 参数 | 含义 |
|---|---|
| `angle_closed` / `angle_open` | 角度映射：合盖 / 全开对应的角度（默认 10 / -90，**尚未用真实角度标定**） |
| `blur_spread` | 模糊扩散系数（越小越通透） |
| `darkening` | 随间隙变暗的强度 |
| `eye_dist_h` | 视点距离（屏幕高度的倍数） |
| `max_tilt_deg` | 最大倾角（默认 60；**调大到 70 以上画面会开始整片变黑**，88 就是原版那种"折到底全黑"） |
| `capture` | 抓屏后端：`auto`（优先 DXGI，失败回退 GDI）/ `dxgi` / `gdi` |
| `win_shrink_px` | 窗口比屏幕少几像素（默认 2，**DXGI 抓屏的前提**；200% 缩放下必须 ≥2，见上文第 7 条） |
| `refresh_hz` | 抓屏刷新率（默认 30；DXGI 下建议 15~30，GDI 下建议 ≤3） |
| `visible_eps` | 浓度阈值：≤ 它就把玻璃收起（默认 0.005，即 0.5%），见第 12 条；设 `-1` 可恢复常显 |
| `hidden_refresh_hz` | 收起时的"保活"抓屏率（默认 **0** = 完全不抓；设 1 可让抬起时的贴图更即时，代价是收起期间仍有少量 CPU） |
| `keep_on_top_hz` | 每秒重申几次"置顶"（默认 2；任务栏也是置顶窗口，点它会压到玻璃上面，见第 11 条） |
| `lock_at_close` | 合盖到底自动锁屏（默认关） |

## 已知坑

详见 [AGENTS.md](AGENTS.md)（GL 窗口必须继承 `QOpenGLWidget`、截图反馈污染与自排除、bat 文件禁中文等）。

本副本调试过程中额外踩到、值得记一笔的：

- **满屏窗口是"抓屏黑洞"**：恰好铺满物理屏幕的窗口会被 Windows 走"全屏直通"呈现——GDI 抓屏完全看不到它，DXGI 抓屏则把它整块抓成纯黑。所以 `win_shrink_px` 必须 ≥ 1，且 `SetWindowDisplayAffinity` 的自我排除必须真正生效。
- **`#version 330 compatibility` 在 Intel Windows 驱动上会被直接拒绝**：该驱动的兼容模式只到 GLSL 1.20，报 `'varying' : not available in current GLSL version`，程序启动即崩。本项目改用 `330 core` + VAO/VBO，`textureLod` 在 core 下同样可用，**不要**改回 compatibility。
- **抓屏成本决定了效果上限**：只要玻璃处于显示状态，它显示的就是一张截图，帧率上限由抓屏速度决定（GDI ≈30 Hz 封顶、程序内实测 72~84 ms/次；DXGI 单次 6.6 ms）。想更跟手只能换更快的抓屏后端，或改用不做截屏的方案。
- **浓度映射的"黑洞区"**：`max_tilt_deg` 超过约 70° 后，逆投影会让视线大面积射出界面平面，画面成片变黑（88° 时拉满即全黑）。
